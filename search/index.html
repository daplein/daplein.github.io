Search Service Acceptance Testing Spec (v1)

Draft

Working notes migrated from sitecore.search.search-service — mirrors the same structure/style as the repo's integration-testing-v1.md spec. Will iterate here as the design evolves.

Goal

Stand up a first, thin acceptance test in Go, in this repo, that hits a real deployed environment (starting with dev/staging) end-to-end — proving the deployed system is alive and serving real data — replacing the Jenkins-triggered Python suite in Sitecore-PD/sitecore.search.qa.tests for this class of test. This spec captures the auth investigation from today's session and defines the smallest possible first test.

Quick Read

Acceptance tests need a real user token (org-role scopes), not an M2M client-credentials token — confirmed both empirically and by Fanis. Today, the only working path to get that token is a manual copy-paste from a browser session; a scripted login flow is deferred to v1.1, pending credentials for a dedicated portal test user (from Vijay, next business day — different time zone). v1 ships one read-only smoke test (GET /v1/config) authenticated with a manually-supplied, short-lived bearer token, so we can prove the plumbing (env config, HTTP client, CI scaffold) works today without blocking on that dependency.

Relationship to Existing Specs

  • specs/integration-testing-v1.md covers integration tests: local/CI dev stack, dummy JWT middleware, disposable fixtures, build tag integration && e2e.
  • specs/proposal-qa-acceptance-test-consolidation.md proposes migrating most of the QA repo's CRUD/schema/error-code tests into that integration suite, leaving a thin acceptance layer (~8-10 tests) that only proves the live deployed system is healthy and serving real content.
  • This spec is the acceptance-layer counterpart to integration-testing-v1.md: same repo, same language, different target (real deployed environments, real auth, real data) and a separate build tag so the two never run together by accident.

Conclusion: none of the 5 M2M clients in the Identity Client Registry (docs/architecture/security.md §7) carry search.config:r/search.config:m — they're service-to-service or tenant-lookup clients only. Endpoints like GET /v1/config require a real user token with org-role-derived scopes. This is a hard constraint, not a missing-scope-grant fix.

Test Framework (v1)

  • Language: Go
  • Runner: standard go test
  • Assertions: testify (require/assert)
  • Isolation: new build tag acceptance (e.g. //go:build acceptance), kept entirely separate from integration && e2e — different target (real deployed env), different secrets, different risk profile (real prod/staging data). Never run as part of go test ./..., make test, or the existing make test-integration-e2e.
  • Config/secrets: local_dev_env/env/acceptance.env (gitignored; template at acceptance.env.example), following the same per-service .env/.env.example convention already used by local_dev_env/env/*.env.

First Acceptance Test Scope (v1 — today)

Scenario

Authenticate with a manually-supplied bearer token (env var ACCEPTANCE_STAGING_BEARER_TOKEN) and call GET /v1/config against the real dev-eun deployed Config API, asserting a healthy response.

Minimum Assertions

  1. Request succeeds with 200 OK.
  2. Response body decodes as a JSON array.
  3. (Stretch) At least one returned config has the expected shape (id, name, tenantId, status fields present).

Explicitly Out of Scope for v1

  • Any write operation (create/update/delete config) — read-only smoke test only, to avoid mutating real staging/prod data before the login flow (and its cleanup story) exists.
  • Scripted/automated login (browser or ROPC) — token is manually pasted for now.
  • Ingestion/Runtime API coverage — start with Config API only.
  • Multi-environment matrix (staging vs prod) — staging only for v1.

Environment Strategy

  • Target: real deployed dev-eun cluster via its public endpoint (https://api-dev-eun-cdpp.sitecorecloud.io/search-config/v1/config), same environment the sitecore.search.qa.tests "staging" config points at.
  • No local stack, no mocks — this is the point of an acceptance test.
  • Config loading mirrors test/integration/client.go's envOrDefault pattern: all URLs/timeouts overridable via env var, sensible defaults committed.

Secrets Strategy (v1)

  • Local: ACCEPTANCE_STAGING_BEARER_TOKEN in local_dev_env/env/acceptance.env (gitignored), manually refreshed by hand each session (token is short-lived, ~1-24h).
  • CI: not yet wired — v1 is local-only until the login flow (v1.1) exists; CI cannot copy-paste a browser token. Do not add this test to any GitHub Actions workflow yet.
  • M2M client ids from docs/architecture/security.md §7 are not used for this test class — documented here so a future contributor doesn't re-attempt the same dead end.

v1.1 (Next — blocked on Vijay P / portal test user)

  • Replace manual token with a scripted login:
    • First choice: confirm with Vijay whether the staging Auth0 tenant supports a direct Resource Owner Password (ROPC) grant for the dedicated QA portal test user (would avoid a browser dependency).
    • Fallback: port sitecore.search.qa.tests/conftest.py's Playwright-based login (login_and_extract_bearer_staging) to Go (e.g. chromedp), intercepting the /oauth/token response / Authorization header the same way.
  • Store portal test user credentials in LastPass under a clear, documented item name (today's session found no existing documented item for this — it may currently live only in Jenkins credentials, which is why this is blocked).
  • Once scripted login lands, wire this test into a CI workflow (nightly or manual-dispatch only, per specs/proposal-qa-acceptance-test-consolidation.md's guidance to keep acceptance tests thin and infrequent vs. PR-blocking).

Open Questions

  • Which Vijay owns the portal test user credentials (see also the same open question in specs/proposal-qa-acceptance-test-consolidation.md re: Vijay Kalkundri vs. Vijay P)?
  • Should the eventual scripted-login token be cached/reused across a test run (session-scoped fixture, as the Python suite does) or re-acquired per test?
  • Multi-env support (prod) sequencing — same login mechanism, different org/tenant/credentials?

Definition of Done (v1)

  • One Go test, tagged acceptance, runs locally against real staging and passes with a manually-supplied token.
  • local_dev_env/env/acceptance.env.example documents the required env var with no real secret committed.
  • This spec merged/cross-linked with proposal-qa-acceptance-test-consolidation.md and integration-testing-v1.md.
  • No CI workflow changes yet (explicitly deferred to v1.1).
